# Ceremony Playlist Builder

A free, browser-only web app (playlists.roncarmel.com, GitHub Pages, no server) that builds long timed Spotify playlists for ceremony and retreat sessions from the person's own playlists. The owner is Ron, who uses it with clients. It is not public yet, so file formats and wording can still change freely.

## How it works

- Each person makes their own Spotify app (a free Client ID, development mode) and pastes the Client ID in. Sign-in is Spotify's PKCE flow in the browser: no secret, no backend.
- A **recipe** says which of the person's playlists to draw from, in what order, for how many minutes, with silence between segments. The app builds as many playlists from a recipe as the songs allow, each song used once.
- Pyodide runs `engine.py` in the page (songs are picked there). Everything else is plain JavaScript in classic `<script>` files (no build step, no modules, shared global scope).
- Anything the person types goes nowhere but their browser and their own Spotify account. Do not add servers, trackers, or anything that sends their data elsewhere (the only third parties are Spotify, the Pyodide CDN, a Ko-fi support panel, a GoatCounter page-view counter, and a Tally form for problem reports whose address carries scrubbed details). The one exception is the wait relay: see "Spotify's limits" below.

## Decisions worth knowing (and why)

**Saving recipes**
- Recipes live in `localStorage` (`formats`) and are saved there on every edit. By default they are also **saved to Spotify** (`backupMode` unset or "spotify"): one private playlist per recipe named `<title> (recipe)`, the recipe packed into its description ("Holds a recipe, not music. Do not edit." plus dense CJK characters; saves with only "Do not edit." are still read, 14 bits each, magic "CP", version, CRC-16; `SAVE_LIMIT` is 300 characters because Spotify's own app shows 300; the API accepts 512). Saves are found by decoding descriptions, not by name.
- The other choice is **manual backup** (`backupMode` = "manual"): download a text file, restore from one.
- Every recipe has a `revision` and `modified`, written only after its first edit. `mergeFromSpotify` (app.js) settles each recipe against its save using a per-device record `spotifySynced` (`{id: {rev, playlistId}}`): only one side changed means that side wins; both changed, or no record and a difference, opens a **required** dialog (no Escape, no backdrop close). A save that is gone from Spotify asks too (keep or remove). Recipes found only in Spotify are added. Deleting a recipe deletes its save (`spotifyPendingDeletes` survives a closed tab). Unreadable saves are rewritten in place if they have the recipe's name, and never deleted.
- Saves are debounced 5 s with a 30 s maximum wait, flushed when the page is hidden, retried when the connection returns, paused while a build runs. A second failure in a row, or an unexpected one, opens a popup (back up now / try again / report / close).
- **Covers** (`recipe-cover.jpg`) are queued and sent after a save is done, one at a time, never waited for: a rate-limited upload stops the rest quietly and they go with a later save (`uploadCovers`, `noWait` on `spotifyRequest`). A save rewritten from the old "Do not edit." note gets the new cover once even though it has one (`recipeCoverDue` in localStorage until sent).
- Wording rule: say nothing about where the recipes are kept, like a Google Doc ("Saved to Spotify"). The exceptions are the manual backup option, the Privacy section, and Reset app on this device, which must say what they erase.

**Messages**
- One place for messages: the line under the editor's colored bar (`#feCaption`), which normally shows "N min of music + N min of silence" (hours from an hour up). `showNotices` takes sentences (shown in turn, with "(1 of 3)") or objects with `hold: true` (kept until used, dismissed, or the recipe is edited). `attentionItems()` in app.js lists trouble that stays until fixed (failed save, unreadable saves, too-long recipe, cover problems). A message about something the person just did (`transient`) comes first. Messages wait while the person is editing. Crossfade between texts, none under reduced motion.
- The ⋯ menu button crossfades to `backup-cover.jpg` while a save runs, for at least a second. No dots or badges anywhere. While the cloud shows, the button's border is transparent (it showed as a pink rim).
- The first time a save writes a recipe to Spotify, a pointer hangs under the menu button: "Recipes automatically save to Spotify as you edit. You'll see this cloud while saving." and Got it (`offerSaveTip`/`showSaveTip` in editor.js, `fe-st-*`). The button keeps the cloud while it is open, and the rest of the page is blurred 1 px (a hole 6 px larger than the button, so its pink is not smeared). It waits for quiet (no popup, menu, build, focus in a field, 3 s since the last edit), blocks nothing, closes on any click, tap or key, and never shows again (`saveTipShown`, set when it opens). Not in manual mode. Decided by Ron, 2026-11-04, over a "Saving..." status line.
- Dialogs that need an answer are `askSyncChoice` (editor.js); `required: true` makes them undismissable.

**Startup and versions**
- The inline script in `index.html` shows a popup (`#startupProblem`) when the page's scripts did not start or disagree on version. The first time in a visit it fetches fresh copies of the page and every script (`cache: "reload"`) and loads the page again by itself (`startupRefreshed` in sessionStorage); a clean start clears that mark.
- Back from Spotify's sign-in (`?code=` in the address) the `<head>` script puts up `#connectingScreen` over the app page: the icon and four steps (signing in, playlists, recipes, Python; recipes hidden in manual mode), each ticked by `connectingStep` as it finishes. The first time ever (`firstConnect`) it ends on Setup complete! and waits for its button (`setupComplete`): "Let's make a recipe!", or "Show me my recipes!" when recipes already exist, as after setting up again on a new device or in an iPhone's Home Screen app (decided by Ron, 2026-11-04). It stays until connected, the first save (merge) is done and Python is ready (Python loads alongside the sign-in), then fades. The first time ever (no `connectedBefore` when the page loaded: the end of setup) it does not fade: the icon gives way to a pink check, "Setup complete!" sits over the four ticked steps, and it waits for its button, Let’s make a recipe! (approved first person plural; `setupComplete`, `firstConnect`; a user test found the editor arriving by itself left setup feeling unfinished; decided by Ron, 2026-11-04). A failed step skips this. No time limit: each step finishes or fails. A failed step shows a muted ✕ for a moment, then the screen goes and the problem shows as usual; any `askSyncChoice` takes it down at once (`connectingScreen` in app.js). Every Spotify request that gets no answer fails after 30 s (`fetchWithAnswerLimit`, "Spotify did not answer").
- Sign-in lasts between visits: Spotify's refresh token is kept in `localStorage` (`spotifyRefresh`, with its Client ID and permissions). With no sign-in in the tab, or on a 401, `renewSignIn` renews it in the background without leaving the page (one at a time; a refusal forgets it, no answer keeps it). Disconnect forgets it. This is not the decided-against auto-connect: nothing goes to Spotify's page by itself.
- When there is still no working sign-in on the app page (renewal refused, Disconnect, an expired sign-in), the app blurs and dims behind `#reconnectScreen`: the icon, "Spotify needs you to sign in again." and Reconnect to Spotify, which runs the usual sign-in and connecting screen. `<main>` is inert meanwhile. Not shown for network or Premium problems (their own Try again). The button is not focused by the app (a focus ring showed on load).
- After a clean start, and when the person returns to the tab after more than 10 minutes, the page fetches `version.txt`. A different stamp with nothing going on reloads once per new stamp (`versionTried`); otherwise a held message offers Reload. No timers. Opening the ⋯ menu also asks (at most every 30 s); a newer version turns the menu's last line into a pink box, New version available / You have <stamp> / Update (`versionLine` in editor.js), and an open menu counts as something going on, so no reload by itself.
- The stamp (e.g. `2026-10-31d`) is in `version.txt`, `APP_VERSION` in `app.js`, five places in `index.html` (a check enforces it), and a few checks in `tests/run.js`. Scripts load as `app.js?v=STAMP`. `python3 bump_version.py` sets every one of them (`--check` says whether they agree); run it for every change that goes to the site.
- Releasing: pushing to `main` publishes the site (GitHub Pages). Git uses HTTPS with the `gh` login at `~/.local/bin/gh`.

**Spotify's limits**
- Spotify does not publish its limits, and a page cannot read Retry-After (Spotify's CORS does not expose it). So the app keeps its own record in localStorage: requests per minute by kind (`spotifyCalls`, 8 days) and each refusal with the requests before it, the last refusal and when it cleared (`spotifyLimits`).
- Songs are added 100 per request (Spotify's documented maximum; it was 10). If Spotify answers 400, the rest of the visit uses 10 and the record notes it.
- After a rate limit with no readable wait, every user's page automatically asks the wait relay (`WAIT_RELAY_URL`, `askSpotifyWait`): one GET /me through Ron's worker, shared by requests refused together and reused for 30 s. Its wait goes into the usual message and the record. Not for cover uploads (their own limit). Disclosed in one Privacy paragraph (`privacyWaitRelay`); decided by Ron, 2026-11-02, as automatic for everyone.
- A wait of over a minute (not for covers) is kept in localStorage (`spotifyPausedUntil`: until, when it began, reason, Client ID) and nothing goes to Spotify until it ends (`spotifyPause`, `tickPause`). The line under the bar turns accent pink with a clock and "Spotify paused · back in H:MM:SS" plus Details (`fe-notice-pause`); the Build button is hidden; the popup (`showPauseDialog` in editor.js: a ring with the countdown and end time that empties as the wait passes, one list of what works and what waits, why) opens by itself only when a wait starts. When it ends the app connects and saves by itself. Recipes stay editable, and the playlist menus use the list kept from the last good connection (`spotifyPlaylists`, no descriptions; Disconnect forgets it). Decided by Ron, 2026-11-02, over a blurred screen.
- Ron's device is known by a SHA-256 hash of his Client ID (`OWNER_CLIENT_HASHES`). There only: a held message offers to copy the record after a refusal or a week, and the menu has Copy Spotify record. Ron pastes the record into the chat for analysis.

**Building**
- A song is used once per playlist and once across the playlists made in one run, compared by ISRC (one recording, whatever release it is on), else Spotify ID (`song_id` in engine.py, `key` on each track; saved songs carry `v: SONGS_VERSION`). A song listed twice in one source counts once. A segment may come in up to 10% short; below that the plan says so instead of repeating songs.
- To get the most playlists from overlapping sources, `pick` takes songs only its own source has first, and `fill_order` fills the segment with the least to spare first.
- Before building, songs whose artist and title match (case, accents, punctuation and a remaster note ignored) in different recordings are mentioned as information (`findSuspects`), with links that open the playlist at the song. The app never guesses that two recordings are the same song.
- A source that lists a song more than once gets a box saying so, the songs behind Details (`findRepeats`). The app does not change the person's source playlists: Spotify removes every copy of a URI, so a fix would take the song out and put one back, and a failure in between would lose it (decided against).
- Earlier playlists the app made that share names with the new ones are replaced; "Details" opens a line saying replacing is usual and a checkbox that keeps them instead, renamed to `<name> (version a)` (next letter each time). The person's own playlists that have names the new ones use are always renamed that way, first.
- Playlists are named `<recipe name> N`. So New recipe asks for a name first (`askNewFormat`: a pink capsule like the tab, with its triangle; no default, since "Recipe 1" made "Recipe 1 1"; blank or another recipe's name is not accepted). While the popup is open the new recipe is already there as a draft (`draft: true`), selected, its tab with the pencil following the name behind the dim; drafts are never written (`modelToText`) or saved, and Cancel removes it. Built playlists carry a description marker (`APP_MARKER`) so the app knows they are its own. The description (`builtDescription`) is the marker first, then "Please do not edit this description..." and "Playlist 3 of 5, built 4 Nov 2026." Nothing else: no segments, no links (decided by Ron, 2026-11-04).

**The build popup**
- One popup (`#createDialog`, classes `bd-*`) for the whole build: a strip of steps (Read songs, Plan, Build, Done), then one plain list of playlists (no lines, no bars; the shape bars were dropped once songs went in one request, 2026-11-03). The plan shows no list, only how many (a user test found the planned names confusing; decided by Ron, 2026-11-03); the list appears when Build is pressed and shows progress (not built: grey name, nothing on the right; under way: spinner and the step in pink; built: tick, songs and length). While building, a count is pinned at the top (`#bdTally`, `setTally`): "3 of 17 playlists", "Keep this tab open." and a tile per playlist, lit when made, breathing while under way; one playlist says "Building your playlist" with no tile. The list follows the row being built until the person scrolls it, and at the end it scrolls back to the top. Boxes above the list (see below).
- With one recipe that can make more than one, the person chooses how many (decided by Ron, 2026-11-03, because people were confused about why several): "The playlists you chose for this recipe have enough songs to build up to N playlists." with Why N? at its end (or "You can build up to N playlists from this recipe." when More options' limit set it), a grey line on what several means (no song repeated, helps long term clients), then "Choose how many playlists you'd like to build from this recipe." and a button per playlist (a tile with its number above, up to 8 in a row; choosing 3 lights the first three; `bd-pick-*`, `choosePlaylists`). None is chosen at first: Build says "Build playlists" and does nothing until one is (decided by Ron, 2026-11-04, replacing a slider). Fewer builds the first ones; earlier playlists from the recipe are still replaced as a set. One possible, or several recipes, keeps "Ready to build N playlists. Why N?" on one line. Why N? opens a table right under that first sentence: per source playlist, minutes per playlist, minutes it has, how many playlists that is enough for (`sources`), and how many songs are in more than one source (`shared`).
- Messages before the list are compact boxes (`.bd-info`, built by `fillInfoBoxes`), each with an accent icon (not a warning), long parts behind "Details". The popup's text can be selected. One Build button.
- When a build is done, a finale (`showFinale`, in `#actionMessage`): the cover fanned out as cards (one per playlist, five at most: more look the same and a wider fan leaves a phone's popup) with a pink glow, "N playlists", the music (not silence) counting up over a second, "are in your Spotify library.", a tile per playlist that ripples once (none for one playlist). It plays once in about two seconds: the stack rises and fans out, confetti bursts from behind and falls away. Reduced motion shows the end state. Before it starts, the list glides back to the top (`glideToTop`), so the finale plays in view. Then a pill "Open in Spotify" to the first new playlist (its https address: the app on phones, the web player on computers), the thank-you box with the Support me button, and the list (names are not links). The footer has only Close.
- A recipe that makes nothing lists every reason at once (no playlist chosen, missing, not yours, too short, or enough minutes whose song lengths cannot come within 10% of a segment: `fit`), found partly by minutes alone (`source_needs`).
- When something fails during a build, the build stops. No recovery and no extra buttons: what went wrong, what was built, what to do ("Building again replaces the ones made so far"), and Close. Only an unexpected error offers the report link (`buildProblem`).

**Interface**
- **Three pages in one**, chosen by a class on `<html>` (`page-welcome`, `page-setup`, `page-app`): an inline script in `<head>` picks it before anything is drawn, and `pageName()`/`showPage()` in app.js follow changes. Signed in or `connectedBefore` means the app; `setupStarted` ("1" after Start setup, "0" after Back) means setup; otherwise welcome. `setupAgain` (sessionStorage) is the setup page opened from the menu's Change Client ID. Start setup and Change Client ID push a history entry so the back button returns.
- The app page is always compact (body class `minimal`); the old full view and its Compact view setting are gone. The ⋯ menu: app header, More options, About this app, Privacy, Report a problem (each opens in `#infoOverlay`: the block itself moves into the popup and back; its title sits in a pink band like the menu's header, without the icon), a manual-backup block (only in manual mode), the Spotify row (connected with Disconnect / connecting / Connect Spotify), the version. Disconnect asks first.
- With no recipes (a draft counts as one) the editor shows a welcome card (`#feWelcome`, `fe-welcome-*`): "Time to make your first recipe!", "Tap New recipe above to start.", what a recipe is, and a pink triangle under the middle of New recipe that bounces off its bottom edge like a ball with gravity pulling up (squash on contact; `placeWelcomeArrow`, placed again by a ResizeObserver). No button of its own, the app icon only on phones, no "first visit" record. Build playlists is hidden until there is a recipe, and so are all status lines (Python, Spotify, notices: body class `no-recipes`). Decided by Ron, 2026-11-03.
- **A guide for facilitators** (`#guideSection` in index.html, `gd-*`): six topics that each open in place (designed for long playlists, with a link that opens Playlists to start from; what it doesn't do, silence, several playlists with an example of the Why N? table, adding new music, playlists to start from, which links to Ron's public playlists page). It opens in `#infoOverlay` through `openGuide(topicId)` (app.js), which opens that one topic. Four ways in: the menu item above More options with a line under it, the ? beside the silence stepper (`feSilenceHelp`), "Show me how to do that" in the first-segment tip, and "More in A guide for facilitators" in the build popup's line on several playlists (that line names the number chosen). Decided by Ron, 2026-11-04; he may rename it. Its text under each title is grey and indented. Privacy and More options use the same collapsible topics (`gd-topic`, shared CSS), all closed at first and again each time the popup opens (`closeInfo` closes them).
- The old numbered step sections (Connect, Edit, Build, Back up) are still in the markup but hidden on every page.
- A phone and a wide window differ: below 760 px the silence stepper says "30 sec gaps", wide it says the whole sentence; its width is fixed to the widest wording so the buttons never move under a thumb.
- Popups come and go with motion (`initMotion` in editor.js): a dim backdrop fades, a popup's box fades while rising 8 px and growing from 98%, the Support me panel rises from its corner, a menu or list grows out of the button that opened it. Leaving is quicker. Popups shown with `hidden` get it at once (the app's state stays true) and the class `fx-leaving` keeps them drawn while they fade; the editor's popups, which are made and removed, fade out as an untouchable copy (`fx-ghost`, ids removed). All motion uses two curves, `--ease-out`/`EASE_OUT` for arriving and `--ease-in`/`EASE_IN` for leaving; spinners stay linear. None under reduced motion. The startup problem popup has no motion on purpose.
- Parts that open in place unfold and fold (height, margins and opacity): Details in the build popup's boxes and Why N? (`revealSmoothly`), and every `<details>` section (`toggleDetailsSmoothly`, a click listener on summaries). The Why? bubble on the welcome page fades like a menu.
- Popups whose contents change grow or shrink to their new height over about 0.3 s instead of jumping (`smoothResize` in editor.js: the build popup, the menu's info popup, New recipe). Not on opening, closing, a width change, or under reduced motion.
- Lesson: a short class name (`fe-main`) collided with an existing one and turned a title into a pill. Give new blocks their own prefix (`fe-bk-*`, `fe-sp-*`, `fe-notice-*`).

## Writing and working style (Ron's preferences)

- Never use em dashes or en dashes in any text, including page text, comments and docs.
- Page text: no first person except where already approved; plain, brief, specific; no hedging.
- Recipe and playlist names are never in quotes. Inside a sentence a name is italic: write it as `named(name)` (editor.js; invisible Unicode isolate marks) and show the text with `putNamed` or `feEl`'s `text`. A name on its own (a title, the old → new rename list) is plain. The description on built playlists in Spotify has no quotes either. Decided by Ron, 2026-11-03.
- Exception: the first-segment tip's line about using Ron's playlists, and the guide's Designed for long playlists, Adding new music and Playlists to start from, speak in Ron's voice (decided by Ron, 2026-11-04).
- Exception: anything about supporting Ron (for example the caption "Everyone is welcome to use this app...", the "Support me" buttons, the thank-you box after a build, the Ko-fi panel labels, and any new support text) speaks in Ron's own voice on purpose, and may use the first person.
- Page text says "click" or "tap" by device (`actWord` in app.js; `<span data-act>` in the markup), never "press".
- Support wording: page text says "support" and "Support me", never "donate" or "donation" (identifiers such as `donateHidden`, `createDonate` stay as they are).
- Answers to Ron: brief, essentials only; answer what was asked. Say what was done and what is next. Do not report passing tests (only failures), and do not report time breakdowns.
- For anything visual, show a mockup early (screenshots of the real page with Playwright, Spotify stubbed with `page.route`) and let Ron pick before building. When he says "let's discuss", discuss and do not build.
- Flag language that suggests an AI has feelings or personhood.

## Tests

See `tests/README.md`. Ron wants credit use kept low, so run the whole suite very rarely: only when Ron asks, or before a release after large or wide-reaching changes, and say why first. After an ordinary change, run only the areas it touches (`node run.js "--only=..."`). Read only the failures and the last lines of the output, never the full PASS list. New behavior gets new checks in a named area; when wording changes, update the checks that read it.
